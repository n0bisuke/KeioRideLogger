## 計測の主軸

このアプリの中心は、京王ライナー乗車中にAndroidの携帯網・通信状態を記録し、移動に伴う変化を確かめることです。GPSとセンサーは時刻・移動状態を対応づける補助データとして使います。

- **在圏セルの変化:** 登録済みセルのRAT、利用可能なセル識別情報、時刻を記録し、周辺セル観測とは区別する。`registered=true`の変化だけを切り替わり候補にする。
- **電波品質:** 現在のRSRPに加え、端末/APIが返すRSRQ・SINR等を取得できる範囲で保存する。未取得値は空欄で表す。
- **通信状態:** Androidの既定ネットワークが携帯網・Wi-Fi等のどれか、インターネット接続が検証済みか、その変化時刻を記録する。
- **応答性:** 小さなHTTP(S)プローブの応答時間、成功・失敗・タイムアウトを測り、電波品質や在圏セル変化と時間軸で比べる。
- **移動コンテキスト:** GPSの位置・速度・精度を使って、電車の移動中に起きた通信変化をあとから対応づける。

GPSだけで完結する位置記録アプリにはしません。携帯網の値や通信応答が取得できない場合も、その状態を明確に記録し、架空のhandoverや応答時間を補いません。

## 実機確認ログ（2026-10-30）

### セッションCSV

- 実機で約68秒間記録。CSVは2,853行で、画面のイベント数と一致。全行を読み取れ、明白な破損・途中切れは見つからなかった。
- GPSは28件取得。測位精度は約7〜79 mで変動し、速度はほぼ0。
- ジャイロ約20.3 Hz、磁気約5.0 Hz、気圧約1.0 Hz。加速度は862件、実測約12.7 Hzで、目安の20 Hzより低かった。
- 携帯網イベントは170行。LTE/RSRP等の値は含まれたが、全行`registered=false`。アプリは「在圏セルの情報なし」と表示した。
- 計測停止後、画面ではセンサーが「利用可」となり、最終取得時刻が「0秒前」のまま残る場合があった。

### 2回目のセッションCSV

- 約302秒間記録。CSVは13,095行で、全行を読み取れた。
- 加速度約12.69 Hz、ジャイロ約20.31 Hz、磁気約4.99 Hz、気圧約1.00 Hz。加速度の低い頻度は2回目も再現。
- GPSは243件記録され、計測時間の大部分で約1 Hz。
- 携帯網イベントは1,063行、301個の観測時刻。全行`registered=false`で、在圏セルは確認できなかった。セル値には同一の疑わしい値が繰り返され、他の値もあったが、いずれも登録済みではなかった。

### ADB診断

- アプリの`ACCESS_FINE_LOCATION`と`READ_PHONE_STATE`は`granted=true`。
- 診断時点で電話サービスはLTE `IN_SERVICE`。Androidシステム側のtelephony registryに登録済みLTEセルが見えた。
- 2回目のCSV取得後にもシステム状態を確認。telephony registryにはLTEセル8件（登録済み1、未登録7）が見えた。
- ADB診断はアプリの計測停止中だったため、システム状態とCSVは同時刻の比較ではない。次回調査では計測中に照合する。
- セル識別情報、位置、加入者識別子はログに残さない。

### 確認済みの問題・制約

- **UI不具合:** 計測停止時に画面tickerも止まるため、センサー/GPSの最終取得経過時間が停止時点で固まる。古い値を「0秒前」と誤認させる場合がある。端末設定ではなくアプリ側の状態更新による。
- **携帯網の未解決事項:** 2回のCSVで計1,233行を記録したが、すべて未登録セルだった。権限は許可され、システム側には登録済みLTEセルが見えるため、アプリの取得経路を優先して調べる。ただし、システム診断とCSVは同時刻ではない。Androidは周辺セルも返すので、登録状態を無視して在圏セルと表示しないこと。`CellInfo.isRegistered()`の仕様は[Android API](https://developer.android.com/reference/android/telephony/CellInfo)を参照。
- **加速度レート:** コードは20 Hz相当を要求しているが、この端末での実測は約12.7 Hz。端末の配信周期かアプリ処理か未特定。API要求値だけで達成済みとみなさない。
- **データ保護の懸念:** ファイル名が秒精度のため、同じ秒に連続して計測を開始するとファイルが衝突し、既存CSVを上書きする可能性がある。今回のセッションでは発生していない。

**取得経路の対応状況（2026-10-30）:** 有力な仮説は、`requestCellInfoUpdate()` が TelephonyManager に紐づいた回線のモデムにしか問い合わせないこと（旧実装は既定の TelephonyManager を使っていた）。データ通信の回線（`getDefaultDataSubscriptionId()`）に紐づけた TelephonyManager で要求するよう変更した。比較のため、全モデム分の `allCellInfo`（`src=cached`）と `CellInfoListener`（`src=listener`、Android 12 以降）も並行して取得する。経路ごとに `cell_poll` 行（総数・在圏数・方式別件数・`ok`/`empty`/`no_response`/`error` のみ）を記録する。`cell` 行には `src=` を付け、副経路は在圏セルだけを記録する（重複は除外）。開始時の `cell_status` 行には、回線の有効性、データ回線と既定回線の一致、アクティブな回線数、モデム数、SIM 状態、データ網種別、サービス状態を真偽値・件数・列挙名で記録する（識別子は記録しない）。画面は「在圏セルあり／観測データあり（在圏セルなし）／観測データなし（空の応答）／応答なし（5 秒）／エラー」を区別する。周辺セルは件数だけを表示し、在圏セルとしては表示しない。**実機での確認点:** 計測中に、`cell_poll` で `src` ごとの `registered=` の値を比べる。`request` が 0 で `cached` または `listener` が 1 なら回線の紐づけの問題、全経路で 0 なら端末・API 側の問題と切り分けられる。計測中に ADB でシステム側の状態も確認する。「同一の疑わしい値の繰り返し」は `age_ms` と `cell_poll` の件数で、キャッシュの再返却かどうかを判断できる。
