対象: `GpsCollector.onLocationChanged()`、`RecorderViewModel`、GPSカード。

- `GpsCollector`は開始時に`gps_status=waiting`を記録して「受信待ち」を表示するが、測位成功時に状態イベントも表示ラベルも更新していない。GPSコールバックで初回測位を検知し、「測位中」など成功状態へ遷移させる。

- 測位が始まる前、位置情報/GPSが無効、権限なし、測位後に更新停止、計測停止の状態を分ける。状態遷移は必要に応じて`gps_status`にも時刻付きで記録する。

**確認ログ（2026-10-30、秋葉原のカフェ周辺で屋外・短時間検証）:** CSVは約52秒、2,573行。GPSイベント46件、中央値約1秒間隔（最大約1.54秒）、水平精度2.6〜5.6m、速度0〜約1.18m/s。位置情報は実際に取得できている。一方`gps_status`は開始時の`waiting` 1件だけで、測位成功状態の更新がない。`GpsCollector.onLocationChanged()`はGPS値を渡すが、`RecorderViewModel`の`gpsStatus`を変更していないため、画面が「受信中」のまま残る原因はアプリ側の状態更新漏れと判断。端末設定の問題を示すデータではない。生CSVの位置・識別情報はこの公開ログに記録しない。

**完了条件:** 屋外でGPS取得を開始し、初回測位後にGPSカードが成功状態・最終更新時刻・精度を表示する。受信待ち、位置情報オフ、権限なし、測位後の更新停止、停止後が混同されず、CSV状態イベントと画面表示が一致する。GPSが届かない屋内状態でも他のセンサー・携帯網記録は継続する。

### [ ] P2: 加速度の実測周期を調査して利用者に伝える

対象: `MotionSensors.kt`。

- `Sensor.minDelay`等の端末能力と`SensorEvent.timestamp`間隔を照合し、約12.7 Hzになった理由を確認する。
- 端末が20 Hzを出せない場合は、UIまたはCSVに実測レートや端末上限を示す。
- 根拠なくポーリングや頻度を上げて電池消費を増やさない。

**完了条件:** 端末が提供できる周期とアプリが記録した周期を区別して説明できる。取得レートが不足する端末では制限を明示する。

**対応状況（2026-10-30）: 実装済み・実機確認待ち。** アプリ側の原因が濃厚。旧実装は「前回採用したサンプルから 45 ms 未満なら捨てる」という間引き方式で、端末が 25 Hz（40 ms 間隔）で配信すると1つおきに捨てられて 12.5 Hz になる。2回の実測（12.7 Hz、12.69 Hz）と一致する。目標周期の時間グリッドで間引く `RateLimiter` に置き換えた（`RateLimiterTest`：25 Hz 入力で 20 Hz になる。旧方式なら 12.5 Hz で失敗する条件）。電池消費を増やす変更（要求周期の短縮、ポーリング）はしていない。端末からの配信頻度（`received_hz`）と記録頻度（`recorded_hz`）を分けて数え、画面に表示するとともに停止時に `sensor_rate` 行へ記録する。開始時の `sensor_status` 行には `min_delay_us`、`max_delay_us`、`fifo_max` を記録する。配信が目安の 90% を下回るときは画面で知らせる。**実機での確認点:** 加速度の `sensor_rate` で `received_hz` が約 25、`recorded_hz` が約 20 になれば見立てどおり。`received_hz` 自体が 20 未満なら、端末側の制限になる。

### [ ] P1: 在圏セルの切り替わりを履歴・件数で確認できるようにする

対象: `CellCollector.kt`、携帯網カード、CSV。

- `CellCollector`はすでに登録済みセルの変化を`cell_change`としてCSVへ出している。このイベント生成を確認して再利用し、携帯網カードまたはCSV可視化で切り替わり件数・履歴を見られるようにする。
- セル観測と「在圏セルの切り替わり」を分け、`registered=false`の周辺セル変化を切り替わりとして数えない。最初に得た登録済みセルは基準値として扱い、それ自体は切り替わり件数に含めない。
- 登録済みセルが変わった場合、RATと利用可能なセル識別子・PCI・周波数情報で比較し、時刻付きで履歴を記録する。
- 登録済みセルが取得できない場合は切り替わり回数を増やさず、「在圏セル情報なし」と分かるようにする。APIの更新制限により見逃しがあり得るため、完全なハンドオーバー捕捉とは表示しない。
- 位置・加入者識別子など、切り替わり判定に不要な情報は診断ログへ追加しない。Cell IDを画面やCSVに残す場合も、ユーザーの端末内の計測データとして扱う。

**完了条件:** 登録済みセルが観測される端末・経路で、初回セルは基準値となり、同一セルの繰り返しを重複カウントせず、登録済みセルの変化だけが履歴に出る。すべて未登録セルのときは「確認できた切り替わりなし」と「在圏セル情報を取得できず」を区別する。実機の無線網切り替えと完全一致する保証は付けない。

**切り替わり判定の対応状況（2026-10-30）: 実装済み・実機確認待ち。** 判定を `ServingCellTracker`（Android に依存しない）に切り出した。最初の在圏セルは基準（`cell_change` の `status=baseline`）で、数えない。同じセルの繰り返しと、`registered=false` のセルは数えない。比較は方式が同じなら、Cell ID・PCI・ARFCN のうち両方に値がある項目だけで行う。比べられる項目がないときは `indeterminate` として数えず、基準も変えない。`switched` 行の `note` に累計回数と直前のセルを残す。画面の携帯網カードには回数と直近5件の履歴（時刻、方式・PCI・ARFCN）を出す。在圏セルを一度も得られていないときは「在圏セル情報を取得できず（判定できません）」、得られて変化がないときは「確認できた切り替わりなし」と区別する。見逃しがありうることも画面に明記した。単体テスト `ServingCellTrackerTest` 9 件合格、UI テストはコンパイルのみ確認。

**追加実機確認（2026-10-30）:** 約10分の低速/停止に近いCSVで`switched`が2回出た。ただし約0.6秒に`listener`が別セルを1回だけ返し、直後に元へ戻った。`request`/`cached`経路は切り替わり前後で同じ在圏セルを示した。このイベントは「観測された登録セル変化候補」であり、ハンドオーバー確定とは言えない。実乗車データで継続性を確認し、必要なら単発・経路限定の変化と複数回/複数経路で裏付けられた変化を表示上区別する。HTTP probe timeoutとの時間的な近さも、プローブ間隔の制約があるため因果関係を示す証拠にはしない。

### [ ] P2: 単発・一経路だけのセル変化候補を実乗車で検証する

対象: `CellCollector.kt`、`ServingCellTracker`、携帯網カード。

- 最新CSVでは`listener`経路だけで別の登録済みセルが1回観測され、約0.6秒で元へ戻った。他の経路は前後で元のセルを示した。このような単発観測を「確認済みhandover」と表示しない。
- 計測経路ごとの最新観測時刻・登録状態を並べ、各経路が同一時刻に返した値であるかのように混同しない。
- 実乗車中に同じ現象が再現するか確認する。仕様や追加データなしに短いイベントを機械的に捨てず、「観測候補」と「複数回/経路で裏付けられた変化」の表示を検討する。
- HTTP probe timeoutとセル候補が近い時刻に出ても、probe間隔とタイムアウトの幅を考慮し、相関を確定原因として表示しない。

**完了条件:** 乗車中CSVでセル観測の継続性を経路別に説明でき、単発・不一致な観測がハンドオーバー確定表示と混同されない。実装方法を変える場合は`ServingCellTracker`の既存テストと表示仕様を更新する。

**取得経路の対応状況（2026-10-30）:** 有力な仮説は、`requestCellInfoUpdate()` が TelephonyManager に紐づいた回線のモデムにしか問い合わせないこと（旧実装は既定の TelephonyManager を使っていた）。データ通信の回線（`getDefaultDataSubscriptionId()`）に紐づけた TelephonyManager で要求するよう変更した。比較のため、全モデム分の `allCellInfo`（`src=cached`）と `CellInfoListener`（`src=listener`、Android 12 以降）も並行して取得する。経路ごとに `cell_poll` 行（総数・在圏数・方式別件数・`ok`/`empty`/`no_response`/`error` のみ）を記録する。`cell` 行には `src=` を付け、副経路は在圏セルだけを記録する（重複は除外）。開始時の `cell_status` 行には、回線の有効性、データ回線と既定回線の一致、アクティブな回線数、モデム数、SIM 状態、データ網種別、サービス状態を真偽値・件数・列挙名で記録する（識別子は記録しない）。画面は「在圏セルあり／観測データあり（在圏セルなし）／観測データなし（空の応答）／応答なし（5 秒）／エラー」を区別する。周辺セルは件数だけを表示し、在圏セルとしては表示しない。**実機での確認点:** 計測中に、`cell_poll` で `src` ごとの `registered=` の値を比べる。`request` が 0 で `cached` または `listener` が 1 なら回線の紐づけの問題、全経路で 0 なら端末・API 側の問題と切り分けられる。計測中に ADB でシステム側の状態も確認する。「同一の疑わしい値の繰り返し」は `age_ms` と `cell_poll` の件数で、キャッシュの再返却かどうかを判断できる。

### [ ] P1: 通信経路とHTTP(S)応答時間を記録する

対象: 新規`NetworkCollector`、`AndroidManifest.xml`、CSV、計測画面。

**完了条件:** Wi-Fi/携帯網の違いとネットワーク状態変化がCSVで識別でき、応答時間とタイムアウトが時刻付きで記録される。通信不能時・権限/機能制限時にもGPS/センサー記録は継続する。

**対応状況（2026-10-30）: 実装済み・実機確認待ち。** 接続先と間隔はユーザーの確認を経て決定した（`https://connectivitycheck.gstatic.com/generate_204`、10 秒ごと、全体で 5 秒のタイムアウト、毎回新規接続）。`NetworkCollector` を追加した。`registerDefaultNetworkCallback` で既定ネットワークの経路と `NET_CAPABILITY_VALIDATED` を追い、変化があったときだけ `network` 行に記録する（`net=` はセッション内の通し番号）。応答時間は `http_probe` 行に、開始時刻・`duration_ms`・`http_status`・`ok`/`http_error`/`timeout`/`error`・計測時の経路を記録する。計測失敗は記録するだけで、ほかの計測は止めない。停止時にはコールバックの解除と、進行中の計測の打ち切りを待つ。`INTERNET` と `ACCESS_NETWORK_STATE` 権限を追加した。画面の通信カードに経路・確認状態・最新の応答時間・成功回数を表示し、計測開始前ならスイッチでオフにできる。README の「送信しない」という記述は、応答時間の計測を例外として明記するよう更新した。

Androidの既定ネットワークとtransport/capabilitiesは`ConnectivityManager`のcallbackで追跡できます。[公式のネットワーク状態ガイド](https://developer.android.com/develop/connectivity/network-ops/reading-network-state)を参照してください。
