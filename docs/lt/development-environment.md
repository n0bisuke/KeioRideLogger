# 京王ライナー計測アプリの開発環境

## 発表の概要

京王ライナーでの移動中に、Android端末の基地局・電波・通信状態とGPS、各種センサーを記録するアプリを開発しています。開発ツール一式はMac上のOrbStackで動かすLinuxコンテナにまとめ、Android SDKやGradleのビルド環境をホストから分離しています。実機との接続はMac側のADBを使い、コンテナへUSBデバイスを直接渡さない構成です。

実装とビルドはコンテナ内のClaude Codeが担当し、実機での動作確認と画面のスクリーンショット確認はMacホスト側のCodexが担当します。役割を分け、実機で起きたことを見ながら修正を繰り返せる開発環境にしています。

## 構成要素と役割

### Macホスト

- OrbStackを起動し、Docker互換のコンテナ環境を管理する。
- プロジェクトのソースコードをコンテナと共有する。
- 実機へUSB接続し、ホスト側のADBで端末の認識、APKのインストール、画面取得を行う。
- Codexを使い、実機画面やスクリーンショットを確認して、表示・操作上の問題や次の修正点を整理する。

### Android開発コンテナ

- Dockerfileから作成したLinux環境。Android向けJDK、Android SDK Command-line Tools、API 36 SDK、Gradle実行環境、Claude Codeを含む。
- Claude CodeがKotlin / Jetpack Composeの実装、ビルド、コンテナ内で可能なテストや静的チェックを行う。
- Android SDK・Gradleのキャッシュとビルド出力はDocker named volumeに保存し、Mac上のホームディレクトリへキャッシュを作らない。
- ソースコードはホストと共有するため、コンテナ内での編集結果をMac側からも確認できる。

### Android実機

- MacにUSB接続し、ADB経由でビルド済みAPKをインストールする。
- GPS、携帯網情報、電波品質、モーションセンサーなど、実機でしか確認できない計測を行う。
- 計測CSVは端末内で保存し、必要な場合にユーザーが明示的にMacへ取り出して確認する。

## 開発・デバッグの流れ

1. MacでOrbStackとAndroid開発コンテナを起動する。
2. Claude Codeがコンテナ内のソースを調べ、変更を実装する。
3. Claude Codeがコンテナ内でAndroidアプリをビルドし、APKを共有フォルダへ出力する。
4. Mac側のADBでAPKを実機にインストールし、屋内または乗車環境で確認する。
5. Codexがホスト側からADBで画面を取得し、スクリーンショットや画面状態を確認する。
6. Codexが問題点や改善案を整理し、Claude Codeへ渡す作業内容に反映する。
7. 修正版を再ビルドして実機で確認し、必要に応じてこのサイクルを繰り返す。

```text
Mac / OrbStack
├── Android開発コンテナ
│   ├── Android SDK・Gradle・ビルドキャッシュ
│   ├── Claude Code：実装・ビルド
│   └── 共有ソースコード・APK
├── Codex：実機画面の確認・デバッグ整理
└── ADB ── USB ── Android実機
```

## この構成にした理由

- **開発環境を揃えやすい:** JDKやAndroid SDK、ビルドツールをコンテナにまとめ、ホストへの個別インストールを避ける。
- **ホストを汚しにくい:** SDK・GradleキャッシュをDocker volume内に置き、Mac側に大きなビルド環境を残さない。
- **実機の観測を優先できる:** セル情報やセンサー値はAndroid実機で確認し、エミュレータや机上のビルドだけで完成と判断しない。
- **役割を分けて反復できる:** Claude Codeがコンテナ内でコードを変更し、Codexがホストから実機画面を見て確認する。
- **端末接続を単純に保つ:** Android端末はMacへ接続し、ADBでアプリを入れて確認する。コンテナにUSBデバイスを直接渡す設定は不要。

## 発表時に伝える要点

「Mac上のOrbStackでAndroid開発用コンテナを動かし、SDK・Gradle・Claude Codeをコンテナ内にまとめています。コードはホストと共有しますが、ビルド環境とキャッシュはコンテナ側に閉じています。実機はMacへUSB接続し、ホストのADBでAPKを入れます。コンテナ内のClaude Codeが実装し、ホスト側のCodexがADBで取ったスクリーンショットを見てデバッグを支援する、という分担です。」

## 次に図にする際の素材

- Mac / OrbStackの境界
- コンテナ内のSDK、Gradle、Claude Code、ソース共有、named volume
- Macホスト側のCodexとADB
- USBでつながるAndroid実機
- ソース変更 → コンテナビルド → APK共有 → ADBインストール → スクリーンショット確認 → 修正、の循環
- 計測CSVは実機に保存し、必要時だけホストへ取り込むデータ経路

図を作る段階で、構成図と開発サイクル図を分けると、環境の境界と作業の流れが読み取りやすくなります。

## LTデモ要件: 車内で動くライブ可視化

今回のデモは京王ライナーの車内で行う想定です。高尾山付近やトンネルでは携帯回線が不安定になり得るため、ライブ表示をLTE/5G経由にせず、USBケーブルが抜けてもデモが続く構成にします。**デモの本命方式は、Android実機がBLE GATT Serverとして計測イベントを通知し、Mac上のWebアプリがWeb Bluetoothで受け取る構成です。**ローカルサーバーはWebアプリの配信に使い、計測データの中継には使いません。

ただし、先にBLEやWeb画面を作り込まず、実機で計測項目が取得できるか、現在のAndroid画面とCSVでどこまで正確に見せられるかを確かめます。可視化の内容は、実測できた項目と更新頻度に合わせて決めます。

### デモ要件

- 電車内で、インターネット接続・携帯回線・USBケーブルなしに、Android実機からMacのブラウザへ計測値をライブ表示できる。
- AndroidアプリはGPS、在圏セルの状態/観測切り替わり、RSRP等をCSVへ継続保存する。BLEやブラウザに問題が起きてもCSV計測を止めない。
- ブラウザはGPS軌跡、時刻、速度、在圏セルの切り替わり候補、RSRPを同じ時間軸で表示する。在圏セル不明と周辺セルのみの観測は明確に区別する。
- GPS速度に連動するキャラクター演出を追加できるようにする。速度は実測値を使い、停止・加速・巡航・減速を視覚化する。
- 接続・切断状態を表示し、BLE切断後に再接続できる。ライブ表示が欠けた区間も端末内CSVに残る。
- デモ画面・Webアプリ・必要な地図素材を事前に準備し、トンネル内でも機能する。最初の版では地図タイルへの依存を避け、ローカルの軌跡表示と時系列グラフを優先する。
- 発表用に使うデータは、実際の移動データと明示したデモデータを区別する。架空のセル切り替わりや通信品質を実測値に見せない。

### 開発の優先順

1. **実機の取得可否を確認:** 屋外・乗車中にGPS、登録済みセル、RAT、RSRP、取得可能な追加信号値、取得時刻と更新頻度を確認する。周辺セルだけの観測、在圏セルなし、API応答なしを区別する。
2. **実機での見せ方を確認:** Android画面とCSVを使い、地図上の移動、位置精度、セル観測状態、信号値の時間変化をどの粒度で見せられるかを確かめる。実測値が不確かな項目は「未取得」等と表示する。
3. **可視化項目を決める:** 実機で取れた値と安定度を基に、LTで見せる地図・軌跡・セル切り替わり・電波グラフを絞る。
4. **BLEを追加:** BLE GATT Serverから必要なイベントだけ通知し、Web Bluetoothの画面へ表示する。ライブ配信が失敗してもCSV記録は継続する。
5. **車内リハーサル:** ケーブルとインターネットを切った状態で、BLEの接続、再接続、表示更新、トンネル中の継続性を確認する。

### 速度・加速度に連動するキャラクター演出

京王ライナーの速度は一定ではありません。京王電鉄の説明では、ATCが先行列車との間隔、曲線、分岐、下り勾配、停車位置などの条件に応じて適切な速度になるよう制御します（[京王電鉄: 運転保安設備](https://www.keio.co.jp/train/safety/security_feature/equipment.html)）。駅間でも加速・巡航・減速があり、速度や加速度の変化をキャラクターの動きに結びつける演出ができます。

演出例:

- 停車中: キャラクターが座る、眠る、窓の外を見る。
- 発車・加速中: 姿勢を起こし、髪や耳、持ち物が後ろへ流れる。
- 巡航中: 速度に合わせて背景の流れや乗車ポーズの動きを強める。
- 減速・停車前: 前に少し傾き、停車後に落ち着く。
- GPS速度が古い・精度不足・トンネルで途切れた: 速度状態を「不明」にして中立アニメーションへ戻す。古い値で動き続けない。

加速度について、現状のアプリはAndroidの`TYPE_ACCELEROMETER`を記録しており、端末のX/Y/Z軸それぞれに重力を含む値です。端末の向きや手持ちの揺れも含むため、これをそのまま「列車の進行方向の加速度」とは呼べません。Androidには重力を除いた`TYPE_LINEAR_ACCELERATION`もありますが、利用可否や品質は端末で異なり、値も端末座標系です（[Androidモーションセンサー](https://developer.android.com/develop/sensors-and-location/sensors/sensors_motion)）。

そのため、まずGPS速度の時間変化で発車・加速・巡航・減速を粗く表現し、加速度センサーは短い揺れや演出の反応に補助的に使うのが現実的です。進行方向の加速度を計測値として出すには、端末を固定する向き、姿勢推定、列車進行方向への座標変換を実機で検証する必要があります。実験中は生の3軸値と取得時刻を残し、列車由来の加速と乗客の端末操作を混同しないようにします。

速度表示はGPS推定値であり、列車の公式速度計ではありません。1点ごとの値でアニメーションを切り替えるとGPSノイズで表示が揺れるため、時系列平滑化と状態切替のしきい値（ヒステリシス）、数秒の最低継続時間を設けます。しきい値は実車CSVを見て調整し、可視化にはGPS速度とデータの新しさ/精度も表示します。キャラクター演出は実測データを楽しく伝える表現レイヤーとし、セル切り替わりや電波状態の計測値を演出の都合で変更しません。

### キャラクターモチーフ案

添付スクリーンショットにあるのは、高尾山公認のムササビキャラクター「ムッちゃん」です。相棒の「ムサ尾」とともに高尾山や八王子のPRをしているキャラクターなので、今回の高尾山口行きデモに文脈がぴったり合います（[日本ご当地キャラクター協会の紹介](https://gotouchi-chara.jp/chara/mucchan/)、[高尾山マガジンのインタビュー](https://mttakaomagazine.com/interview/vol08)）。

京王ライナーの車両との結びつきなら「しんごくん」も有力です。京王電鉄は5000系車両のキャラクターとして紹介しており、京王ライナーの車両文脈に合います。「けい太くん」は8000系をモチーフにしたキャラクターです（[京王電鉄の発表資料](https://www.keio.co.jp/news/update/news_release/news_release2017/nr180124_goods.pdf)、[京王ライナー開発秘話](https://www.keio.co.jp/zasekishitei/special/story/)）。

キャラクター利用の許可を得られない場合は、**オリジナルのムササビ**を作る案が有力です。高尾山に多く生息し、観察地として知られる動物で、滑空を速度の演出に使えます（[TAKAO 599 MUSEUM: 高尾山のムササビ](https://www.takao599museum.jp/explore/)）。既存のムッちゃんの絵柄・衣装・設定を写さず、独自の造形にします。

| 案 | 分かりやすさ | 速度アニメーションとの相性 | 留意点 |
|---|---|---|---|
| ムッちゃん | 高尾山口・高尾山との関係が明確 | ムササビの滑空で速度を表現できる | 既存キャラクターなので、発表・アプリで使う前に権利者へ利用条件を確認 |
| しんごくん | 京王ライナー/5000系との関連が最も直接的 | 車両そのものとして速度を見せやすい | 公式画像やデザインの利用条件を確認し、許可なく複製・改変しない |
| オリジナルのムササビ | 高尾山の自然と結びつく | 滑空・翼の動きで速度を直感的に表現できる | 京王線そのもののキャラクターではない。オリジナルの造形にする |
| オリジナルの電車キャラ | 鉄道アプリだと一目で分かる | 車体の揺れや加減速を表現できる | 既存車両や公式キャラに似せず独自にデザインする |

**現時点の推し案:** まずムッちゃんの権利者に利用条件を確認し、許可が得られれば高尾山の既存キャラクターとして紹介する。難しい場合は、独自デザインのムササビを使う。京王の車両モチーフも併用する場合、しんごくんは京王電鉄の公式キャラクターなので別途利用条件を確認する。京王電鉄のサイト利用案内は、掲載画像等の複製・改変・二次利用を認めていません（[サイトの利用にあたって](https://www.keio.co.jp/contact/site/)）。

### 想定する構成

```text
Android実機（計測・CSV保存・BLE GATT Server）
       │ BLE通知（近距離、携帯網を使わない）
       ▼
MacのChrome（Web Bluetooth、ライブ画面）
       ▲
       │ localhostで静的Webアプリを配信
Mac上のローカルWebサーバー

USB / ADB：APKインストールと開発時の画面確認に使用。車内ライブ転送には使わない。
```

AndroidのBLE APIではGATT Server役を構成できます。Android 12以降では用途に応じて`BLUETOOTH_ADVERTISE`や`BLUETOOTH_CONNECT`などの実行時権限が必要です（[Android BLE概要](https://developer.android.com/develop/connectivity/bluetooth/ble/ble-overview)、[Bluetooth権限](https://developer.android.com/develop/connectivity/bluetooth/bt-permissions)）。Mac側ブラウザはBLE Peripheralへ接続し、GATT Notificationを受け取るWeb Bluetooth APIを使います。Web Bluetoothは対応ブラウザが限られ、セキュアコンテキストとユーザー操作が必要なので、MacのChromeをデモ対象として事前検証します（[Chrome Web Bluetooth](https://developer.chrome.com/docs/capabilities/bluetooth)、[MDN Web Bluetooth](https://developer.mozilla.org/en-US/docs/Web/API/Web_Bluetooth_API)）。

### 通信・プライバシー・運用条件

- BLEライブ転送はCSV記録から独立させる。BLE停止、ブラウザ終了、接続切断が起きても端末内計測を続ける。
- 送るデータはライブ画面に必要な項目に絞り、センサーの全サンプルを無制限に送らない。GPSは約1 Hz、セル・ネットワーク状態は更新時、信号品質は数Hz程度から検討する。
- Cell IDと正確なGPS座標は機微情報として扱う。ペアリング/接続のユーザー操作を必要とし、見知らぬ端末への常時ブロードキャストや外部サーバーへの送信はしない。
- Webアプリは事前にMacへ用意し、localhostから配信する。インターネットや外部地図タイルがなくても基本デモが成立するようにする。
- 携帯網の応答性を測るHTTPプローブを実施する場合、その結果はBLEデモ経路とは独立した計測値として表示する。BLE通知の遅延を携帯網の遅延として誤認させない。
- 実装前に、対象Android端末のBLE Peripheral対応、Mac ChromeのWeb Bluetooth接続、車内相当距離での安定性、通知頻度、再接続、バッテリー影響を確認する。

### ADB reverse方式との比較

ADB reverseは開発中、USB接続した端末からMacのlocalhostサーバーへアクセスする手段として使えます（[Android: ADB reverseでローカルサーバーへ接続](https://developer.android.com/develop/ui/views/layout/webapps/access-local-server)）。これはポート転送であり、Androidから出たデータをブラウザへ自動で橋渡しする機能ではありません。

ADB reverse経由でライブデータを見せるには、AndroidアプリがHTTP/WebSocketなどでホスト側ポートへ送信し、そのポートをNode.js等のサーバーが受信してブラウザへ配信します。たとえばサーバーがWebSocketを受けてブラウザのWebSocketへ中継します。`adb reverse`だけを実行しても、受信してブラウザへ渡すプロセスがなければ表示されません。USBケーブルとADB接続が前提なので、車内デモの本線にはしません。

BLE直結では、AndroidがGATT ServerのCharacteristicから通知し、ブラウザ内JavaScriptがWeb Bluetooth APIでそのNotificationを受け取ります。計測データを中継するNode.jsサーバーは不要です。WebアプリのHTML/CSS/JavaScriptはローカルHTTPサーバーで配信すればよく、そのサーバーは静的ファイル配信だけを担当します。ブラウザのセキュリティ制約があるため、`file://`で直接開く運用に頼らず、Macの`localhost`で配信する想定にします。

| 方式 | Androidからブラウザまで | Node.js等のデータ中継 | 物理ケーブル | 車内デモでの位置づけ |
|---|---|---:|---:|---|
| ADB reverse | Androidアプリ → USB/ADBポート転送 → ホスト受信サーバー → ブラウザ | 必要 | 必要 | 開発中・予備 |
| BLE + Web Bluetooth | Android GATT通知 → ブラウザ内JavaScript | 不要（静的Web配信だけ） | 不要 | 本命候補 |

BLE方式は部品が少なく、ケーブルや携帯回線に依存しません。ただしWeb Bluetooth対応ブラウザ、BLE接続の許可、再接続処理は必要です。実装段階でMac Chromeと実機の接続確認を行います。まず実機で計測値と画面表示を確認し、その後BLEを追加して、実測CSVの保存とライブ表示を分離したまま進めます。

このライブ可視化はLT向けの追加機能です。先にAndroid実機で登録済みセルと信号値を正しく記録できることを確かめ、その後にBLE送信とブラウザ表示を追加します。ライブ表示が動いても、実測のCSVを正本として保持します。
