# LT資料案: 京王ライナーでAndroid計測、ブラウザでライブ可視化

## 発表で伝えたいこと

京王ライナーで移動しながら、Androidでしか取りにくい携帯網・在圏セルの情報とGPS・センサーを記録し、その記録を残したまま近くのブラウザへリアルタイム表示する。電波の弱い区間やトンネルでも見せられるよう、計測・保存とライブ表示を分けて設計する。

**発表の核:** 「電車の中で、基地局や電波の変化を観測しながら、位置・速度・電波品質をその場で見て、全イベントはCSVにも残す」

## 現状と目標を分ける

| 項目 | 現状 | LTデモ目標 |
|---|---|---|
| AndroidでGPS・セル・信号品質・センサーを記録 | 実機計測・CSV出力で確認中 | 実乗車のデータを使う |
| 計測中の状態表示 | Android画面に表示 | Android画面を補助表示 |
| CSVの後読み可視化 | 要件・実装プロンプトを準備 | ライブ接続失敗時の予備にできる |
| ブラウザへのライブ配信 | 未実装 | BLE GATT通知とWeb Bluetoothを検証・実装 |
| 地図表示 | 未実装 | 外部通信不要の軌跡図から開始。GPS座標を地図上の正確な線路位置とは扱わない |

「実装済み」「実機で確認済み」「計画中」をスライドとデモで明確に区別する。セルが取得できたことと、ハンドオーバーを観測できたことも区別する。

## 7分の発表構成案

1. **導入（30秒）** — 電車に乗っている間、基地局は切り替わるのか、電波や通信応答はどう変わるのか。
2. **Androidを選んだ理由（50秒）** — GPSだけならWebでもよい。Androidの公開Telephony APIで在圏セルや信号強度を観測できる可能性があり、そこを実機で確かめたい。
3. **計測アプリ（60秒）** — GPS、登録済みセル/周辺セル、LTE/NR表示、RSRP等、センサー、通信プローブを時刻付きイベントとして記録。端末やOSの制限で欠ける項目もそのまま扱う。
4. **実測で分かったこと（60秒）** — 手元の実測CSVから確認できた項目・更新間隔・未確認の項目を示す。位置やセルIDなど公開に不要な具体値は伏せる。
5. **ライブ可視化（90秒）** — Androidの計測値をBLEでMacのブラウザへ送り、軌跡・速度・RSRP・セル観測イベントを更新する。Web画面とAndroidの記録状態を並べて見せる。
6. **車内デモを支える設計（60秒）** — BLEで近距離接続し、携帯網に依存させない。CSV保存はライブ表示と独立。トンネルや切断時も記録を継続する。
7. **開発環境と学び（50秒）** — Mac + OrbStack、Android開発コンテナ内のClaude Code、ホスト側ADB/Codex。実機制約を測ってから可視化を設計する。
8. **まとめ（20秒）** — 「移動中の通信品質を、記録を失わず、その場で見える形にする」。今後、複数乗車データや区間比較へ広げる。

## ライブデモで見せる画面

### Android

- 計測中であること、経過時間、記録イベント数。
- GPS・携帯網・センサーの取得状態。未取得とゼロ値を混同しない。
- CSV保存が継続していること。

### ブラウザ

- BLEの接続状態、最終受信時刻、受信データの鮮度。
- GPSの軌跡図と速度。GPS欠測・精度不足を表示する。
- RSRPの時系列。信号が欠測した区間を線で捏造してつながない。
- 登録済みセルの観測変更候補を時刻軸に表示し、周辺セル観測や最初のベースラインと区別する。
- 通信プローブを表示する場合は、HTTP応答時間とBLEの受信遅延を別の指標として扱う。
- 速度に応じてオリジナルのムササビキャラクターを切り替える案は、計測の読み取りを妨げない演出として追加する。

初期版は外部地図タイルを使わず、GPS座標を画面内に投影した「軌跡図」にする。外部通信・APIキー・トンネルでの地図欠落を避けられる。地図背景を将来追加する場合も、オフラインでデモが成立する経路表示を残す。

## ライブ経路とログ経路

```text
                         ┌─ BLE GATT通知 ──> Mac Chrome / Web Bluetooth
Android計測イベント ────┤                       ├─ 軌跡・速度・RSRP・セル観測
                         └─ CSVへ追記            └─ 接続状態・受信時刻
                              │
                              └─ デモ後の保存・事後解析

Mac localhost: 静的Webアプリを配信するだけ。計測データのブリッジにはしない。
ADB/USB: 開発時のインストールと画面確認。車内ライブ転送には使わない。
```

ライブ表示は観客へ現在値を伝える経路、CSVは計測の正本と事後確認の経路。BLEやブラウザの不調を計測停止につなげない。イベント形式を再利用し、CSVとBLEで指標の定義を変えない。

## 実装・リハーサルの段階

1. 実機で計測項目と更新頻度を確認し、実測CSVを保存する。
2. ブラウザでCSVを読む事後可視化を用意し、グラフや軌跡の見せ方を先に確認する。
3. 同じイベントをBLE GATT Serverから通知し、Web Bluetoothでブラウザへ表示する。
4. AndroidのCSV記録とBLE接続を同時に動かし、ライブ表示を切ってもCSVが続くことを確認する。
5. USBを外し、携帯回線を切る/圏外相当の条件でも再接続・欠測表示・計測継続をリハーサルする。
6. 実乗車で画面の明るさ、電池、固定場所、乗客のプライバシー、ブラウザ接続許可を確認する。

### 発表当日の予備手順

- **第一候補:** 実機計測 + BLEライブ画面。
- **BLE接続に失敗:** 事前に保存したCSVをローカルWebビューアで読み込み、実測の事後可視化を見せる。
- **実乗車データを使えない:** 明示したデモデータまたは録画を使い、架空データであることを画面と口頭で示す。
- CSVの予備データは公開リポジトリへ入れない。GPS、時刻、Cell ID等を含む生ログはローカルで管理する。

## 正確さ・公開時の注意

- Androidのセル情報は端末・SIM・モデム・OS・権限に左右される。更新が抑制されるため、すべての切り替えを取れるとは限らない。
- `cell_change`はアプリが観測した変更候補として説明する。イベントがないことだけで「ハンドオーバーがなかった」と断定しない。
- GPS速度は推定値であり、列車の公式速度ではない。トンネル・屋内・精度低下時は不明または古いデータとして表示する。
- RSRP、HTTP応答時間、GPS速度は別々の観測値。相関を示す場合も因果関係を断定しない。
- 生CSV、スクリーンショット、logcat、bugreportは公開Gitへ入れない。サンプルが必要なら座標・時刻・セル識別子を処理した合成または明示的な公開用データを作る。
- Web Bluetooth対応ブラウザとユーザー操作が必要。発表用Mac/Chromeで接続を事前確認する。
