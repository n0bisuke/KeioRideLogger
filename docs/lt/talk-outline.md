# LT資料案: 京王ライナーでAndroid計測、ブラウザでライブ可視化

発表や画面に出る専門用語は、補足資料の[用語集](glossary.md)を参照。
Web画面の実装要件は[LTデモ用Webダッシュボード要件](web-dashboard-requirements.md)にまとめる。
導入と各パートの話のつなぎは[発表者用メモ](presenter-talk-track.md)を参照。

## 発表で伝えたいこと

京王ライナーで移動しながら、Androidでしか取りにくい携帯網・在圏セルの情報とGPS・センサーを記録し、その記録を残したまま近くのブラウザへリアルタイム表示する。電波の弱い区間やトンネルでも見せられるよう、計測・保存とライブ表示を分けて設計する。

**発表の核:** 「電車の中で、基地局や電波の変化を観測しながら、位置・速度・電波品質をその場で見て、全イベントはCSVにも残す」

## 現状と目標を分ける

| 項目 | 現状 | LTデモ目標 |
|---|---|---|
| AndroidでGPS・セル・信号品質・センサーを記録 | 実機計測・CSV出力で確認中 | 実乗車のデータを使う |
| 計測中の状態表示 | Android画面に表示 | Android画面を補助表示 |
| CSVの後読み可視化 | 要件・実装プロンプトを準備 | ライブ接続失敗時の予備にできる |
| ブラウザへのライブ配信 | Android実機からブラウザへの受信とGPS/セル/通信カード表示を確認。軌跡・グラフ連携と切断試験は未確認 | BLEデータを軌跡地図・速度・RSRP・セル変更・HTTP応答グラフへ反映 |
| 地図表示 | 未実装 | 外部通信不要の軌跡図から開始。GPS座標を地図上の正確な線路位置とは扱わない |

「実装済み」「実機で確認済み」「計画中」をスライドとデモで明確に区別する。セルが取得できたことと、ハンドオーバーを観測できたことも区別する。

## 発表構成案（時間は調整前）

1. **OP・自己紹介（40秒）** — 菅原のびすけ、プロトアウトスタジオ、IoTLTの紹介。「作ったものを現場で試す」題材として京王ライナーを選んだことを伝える。
2. **導入と乗車区間（40秒）** — 電車に乗っている間、基地局は切り替わるのか、電波や通信応答はどう変わるのか。Mt.TAKAO 3号の予定時刻を目安に、新宿から高尾山口までの観測を紹介する。
3. **4つの観測テーマ（40秒）** — 在圏セル、トンネル前後、速度と電波品質、気圧・加速度を同じ時刻軸に置いて何が変わるか見る。
4. **Androidを選んだ理由と計測アプリ（70秒）** — GPSだけならWebでもよい。Androidの公開Telephony APIで在圏セルや信号強度を観測できる可能性があり、GPS、LTE/NR表示、RSRP等、センサー、通信プローブを時刻付きイベントとして記録する。端末やOSの制限で欠ける項目もそのまま扱う。
5. **実測で分かったこと（60秒）** — 手元の実測CSVから確認できた項目・更新間隔・未確認の項目を示す。位置やセルIDなど公開に不要な具体値は伏せる。
6. **ライブ可視化とキャラクターデザイン（90秒）** — Androidの計測値をBLEでMacのブラウザへ送り、軌跡・速度・RSRP・セル観測イベントを更新する。Web画面とAndroidの記録状態を並べた後、速度で姿が変わるムッちゃんのスプライトを見せ、けい太くん/しんごくんのデザインを取り入れたオマージュの工夫を紹介する。
7. **車内デモを支える設計（60秒）** — BLEで近距離接続し、携帯網に依存させない。CSV保存はライブ表示と独立。トンネルや切断時も記録を継続する。
8. **開発環境と学び（50秒）** — Mac + OrbStack、Android開発コンテナ内のClaude Code、ホスト側ADB/Codex。実機制約を測ってから可視化を設計する。
9. **まとめ（20秒）** — 京王ライナーで電波を測るところから始まり、GPS・セルの切り替わり・加速度、速度キャラクター、Kotlin/Android開発へ興味が広がったことを振り返る。次はWi-Fiスキャンや、みんなのログで旅のマップを作る構想につなぐ。

## ライブデモで見せる画面

### Android

- 計測中であること、経過時間、記録イベント数。
- GPS・携帯網・センサーの取得状態。未取得とゼロ値を混同しない。
- CSV保存が継続していること。

### ブラウザ

- BLEの接続状態、最終受信時刻、受信データの鮮度。
- GPSの軌跡図と速度。GPS欠測・精度不足を表示する。
- RSRPの時系列。信号が欠測した区間を線で捏造してつながない。
- 登録済みセルの観測変更候補を時刻軸に表示し、周辺セル観測や最初のベースラインと区別する。
- 通信プローブを表示する場合は、HTTP応答時間とBLEの受信遅延を別の指標として扱う。
- 調布付近の地下区間、高尾〜高尾山口間のトンネル区間を、入口/出口の位置を確認してから「トンネル区間（参考）」として地図に重ねる。GPSが切れただけではトンネル進入と断定せず、電波指標・在圏セルの観測変化・HTTP probeと前後比較する。
- Android CSVに記録された端末の3軸加速度と気圧を、ネットワーク指標と同期した補助グラフとして見せる。加速度は端末の向き・重力を含み、気圧は標高そのものではないと説明する。
- BLEライブのセンサー値は生の高頻度データを送らず、気圧の最新値と加速度の短時間要約を必要に応じて追加する。CSVの生ログとは系列を分ける。
- 速度に応じて変わるムササビのイラストも、京王ライナーと高尾山の文脈をつなぐ演出として紹介する。ムッちゃんのムササビらしさと、けい太くん・しんごくんの電車デザインを組み合わせたオマージュであることを伝える。

### 速度で変わるムササビキャラクター

スプライトのモチーフは、高尾山のムササビキャラクター「ムッちゃん」と、京王電鉄の電車キャラクターのデザイン。ムッちゃんの飛膜や大きな尾を残しつつ、車両に乗る姿へ組み合わせたオリジナルのピクセルアートで、公式画像をそのまま貼り合わせたものではない。

### スライド案: 速度が上がると、乗る電車も変わる

**スライドに載せる文案**

> ムッちゃん × 京王電車キャラクターのオマージュ
>
> 通常速度は、けい太くんをイメージした車両に乗って。
> さらに速くなると、しんごくんをイメージした車両に乗り換えます。

**話すポイント:** 速度に合わせてキャラクターを変えるだけでなく、京王電車のキャラクターデザインまで取り入れた。通常速度側はけい太くんのクリーム色・青/ピンクの配色、高速側はしんごくんの銀色・濃いピンクと暗い顔窓をモチーフにした。ムッちゃんの飛ぶ姿から電車に乗る姿へ変化し、高尾山と京王線の両方をひとつの演出に結びつける。

**見せ方:** けい太くん・しんごくんの参考画像を小さく並べ、その下にアプリ用のオリジナルスプライトシートを置く。通常速度側と高速側の2コマを枠で強調する。公式ページのスクリーンショットを公開スライドに転載せず、許諾がない場合はリンクとキャプションで出典を示す。スプライトは[8段階シート](local-captures/mucchan-speed-sprite-sheet-8-stage.png)を使う。

参照: [京王電鉄「けい太くんプロフィール」](https://www.keio.co.jp/keitakun/profile.html)、[高尾山マガジン「VOL08 高尾山公認キャラ ムッちゃん」](https://mttakaomagazine.com/interview/vol08)。

速度分類とイラストの対応案は、停止・歩行・走行・自転車・車・ムッちゃんの最高速風飛行・けい太くん風車両・しんごくん風車両の8段階。Android/Webへの反映は[8段階整理タスク](speed-character-high-speed-task.md)を参照する。これはGPS速度に合わせた演出であり、GPSだけで実際の乗り物を判定する機能ではない。高速道路を走る車も高速域に入る場合がある。

| 段階・表示 | GPS速度の帯（km/h） | イラスト |
|---|---:|---|
| 1 停止 | 1未満 | 翼をたたんだムッちゃん |
| 2 ゆっくり歩き | 1以上6未満 | 歩くムッちゃん（普通歩き段階は統合） |
| 3 走る | 6以上15未満 | 走るムッちゃん |
| 4 自転車くらい | 15以上30未満 | 自転車相当の姿 |
| 5 車くらい | 30以上70未満 | 車相当の姿 |
| 6 京王ライナー高速域 | 70以上90未満 | 元のムッちゃんの最高速風・飛行ポーズ |
| 7 高速域 | 90以上110未満 | けい太くん風車両に乗る |
| 8 超高速域 | 110以上 | しんごくん風車両に乗る |

90/110 km/hの境界は表示演出上の仮案。アプリとWebへの実装後に、同じ速度分類・キャラクターになることを確認する。

京王電鉄の車両そのものの速度を実測・調査した値として「110 km/h」と紹介しない。J-TRECの京王5000系技術資料には、京王線での**運転最高速度110 km/h**と**設計最高速度130 km/h**が記載されている。これは車両・路線の最高速度仕様で、Mt.TAKAO 3号が実際に出す速度や全区間の速度ではない。京王電鉄の公式時刻表はMt.TAKAO 3号の駅時刻を掲載しているが、速度の時系列は掲載していない。LTでは「公表された運転最高速度」と「今回のGPS実測速度」を別の値として示し、アプリ画面のGPS速度を列車の公式速度計のように扱わない。

出典: [J-TREC『京王電鉄5000系電車におけるsustinaコンセプトの適用』](https://www.j-trec.co.jp/company/070/07/jtr07_032-039.pdf)（運転最高速度・設計最高速度）、[京王電鉄 Mt.TAKAO号公式ページ](https://www.keio.co.jp/zasekishitei/index_mt.html)（運行時刻）。

初期版は外部地図タイルを使わず、GPS座標を画面内に投影した「軌跡図」にする。外部通信・APIキー・トンネルでの地図欠落を避けられる。地図背景を将来追加する場合も、オフラインでデモが成立する経路表示を残す。

## ライブ経路とログ経路

```text
                         ┌─ BLE GATT通知 ──> Mac Chrome / Web Bluetooth
Android計測イベント ────┤                       ├─ 軌跡・速度・RSRP・セル観測
                         └─ CSVへ追記            └─ 接続状態・受信時刻
                              │
                              └─ デモ後の保存・事後解析

Mac localhost: 静的Webアプリを配信するだけ。計測データのブリッジにはしない。
ADB/USB: 開発時のインストールと画面確認。車内ライブ転送には使わない。
```

ライブ表示は観客へ現在値を伝える経路、CSVは計測の正本と事後確認の経路。BLEやブラウザの不調を計測停止につなげない。イベント形式を再利用し、CSVとBLEで指標の定義を変えない。

## 実装・リハーサルの段階

1. 実機で計測項目と更新頻度を確認し、実測CSVを保存する。
2. ブラウザでCSVを読む事後可視化を用意し、グラフや軌跡の見せ方を先に確認する。
3. 同じイベントをBLE GATT Serverから通知し、Web Bluetoothでブラウザへ表示する。
4. AndroidのCSV記録とBLE接続を同時に動かし、ライブ表示を切ってもCSVが続くことを確認する。
5. USBを外し、携帯回線を切る/圏外相当の条件でも再接続・欠測表示・計測継続をリハーサルする。
6. 実乗車で画面の明るさ、電池、固定場所、乗客のプライバシー、ブラウザ接続許可を確認する。

## 楽天モバイルのセル情報とMt.TAKAO 3号の時刻を重ねる

### 目指す見せ方

- GPS軌跡を京王線のルート図に重ね、観測した在圏セルごとに区間の色を変える。
- セル変更候補、RSRP/RSRQ/SINR、HTTP応答時間を同じ時間軸に並べる。
- 時刻表の予定時刻に縦線を引き、実際のGPS位置・セル・通信状態を比較する。
- セルIDは画面上では「セルA」「セルB」のような匿名ラベルにし、識別値そのものを発表スライドや公開サンプルへ載せない。
- 基地局位置を出せる場合は、位置の根拠と精度を示す。セルが接続されていた区間と基地局の位置を結ぶ線は「推定」と明示し、実際の電波経路のようには描かない。

### 時刻の基準

京王電鉄の公式ページに掲載されているMt.TAKAO 3号の予定時刻は、新宿11:00発、明大前11:06、高尾山口11:45着です。Mt.TAKAO号は同ページで土休日運行と案内されています。乗車日当日に運行日・時刻・臨時変更を再確認してください（[京王電鉄: Mt.TAKAO号 時刻表](https://www.keio.co.jp/zasekishitei/index_mt.html)）。

- アプリCSVのUTC `time_utc`を日本時間へ変換し、予定時刻のJSTと比較する。
- 計測は新宿発より前に開始し、端末時計を自動設定にしておく。開始時刻を11:00に合わせて相対時間を作るのではなく、実際の記録時刻を使う。
- 予定マーカーは新宿11:00、明大前11:06、高尾山口11:45。GPSで確認した通過・到着時刻を別の実測マーカーとして重ね、遅延や測位誤差を隠さない。
- 明大前以外の駅について公式ページに個別時刻は掲載されていないため、補間した駅到着時刻を公式予定として表示しない。
- 駅到着を自動判定できない場合は、発表者のタップで「乗車」「明大前」「高尾山口」を記録する手動マーカーを予備として用意する。

### 楽天モバイルの基地局データとの照合

現行アプリはCell ID、PCI、TAC、ARFCN/NRARFCN、バンド、登録状態、電波指標を記録します。一方、現在の `CellObservation` とCSVにはMCC/MNCがありません。外部のセルデータベースを照合する前に、Androidの公開 `CellIdentity` APIから得られるMCC/MNCも取得・保存できるか確認する必要があります。MCC/MNC、TAC、セルID、無線方式はセル位置検索に使われる識別項目です（[OpenCelliD: 初回検索に必要な情報](https://docs.opencellid.org/docs/getting-started/first-lookup)）。

照合元の性質は分けて扱います。

| データ元 | 使い方 | 注意点 |
|---|---|---|
| [楽天モバイル公式エリアマップ](https://network.mobile.rakuten.co.jp/area/) | 楽天回線/パートナー回線や4G/5Gのサービスエリア背景を確認 | サービスエリアの予測表示で、個々の基地局の正確な設置地点ではない。実際の受信状況とも差がありうる |
| [OpenCelliD](https://opencellid.net/) | MCC/MNC等による公開セル位置データの照合候補 | コミュニティデータ。セルが未登録の場合があり、APIキー、帰属表示、ライセンス条件の確認が必要 |
| [CellMapper](https://www.cellmapper.net/) | 既存の観測・推定された基地局/セルの参考表示 | ユーザー投稿・推定を含む。ピン位置が未確認または不正確な場合がある |

**現実的な実装順:** まずCSVにMCC/MNCが記録されるか調べ、実測セルの識別子だけをローカルで調べる。発表用には事前に照合した結果をセルA/Bへ置き換えて地図へ重ね、出典と推定精度を表示する。APIキーをブラウザコードや公開リポジトリへ入れず、乗車中に生のGPS/セル情報を外部サービスへ送る設計にしない。

### この比較で分かること・分からないこと

- 分かること: この乗車で端末が観測したセル識別子、信号品質、通信応答の変化と、GPS上のおおよその位置・時刻との対応。
- 条件付きで分かること: 公開データベースに掲載されたセル位置候補。データ元と精度に依存するため、実基地局位置の確定には使わない。
- 分からないこと: セルの位置だけから、端末がその基地局へ接続した電波経路や、無線網内部のハンドオーバー手順を確定すること。
- 「予定時刻にセルが変わった」といった因果は、1回の乗車だけで結論づけず、実測イベントと予定時刻の近さとして示す。

### 楽天モバイル公式エリアマップのスライド

添付スクリーンショットのように、楽天モバイルの公式サービスエリアマップで「高尾山口駅」を検索し、駅ピンを表示した画面を導入スライドの背景説明に使う。ここでのピンは**目的地の高尾山口駅**であり、楽天モバイルの基地局位置ではない。公式マップはサービスエリアの概況を示すもので、個別セルの接続先や車内の実測品質を表すものではない。

表示時には、出典として[楽天モバイル サービスエリアマップ](https://network.mobile.rakuten.co.jp/area/)を明記し、スクリーンショットに記載されたデータ基準日（2026年9月30日時点、2026年10月13日更新）も添える。楽天公式ページは、掲載コンテンツの無断複製・配布・公衆送信を禁止している。そのため、この公開リポジトリにはスクリーンショット画像を複製せず、発表時は公式ページをブラウザで直接表示するか、画像をスライドへ転載する許可を権利者へ確認する（[楽天モバイル サイトポリシー](https://corp.mobile.rakuten.co.jp/guide/sitepolicy/)）。

**スライドの役割:** 公式のエリア概況を先に見せ、その上で「実際にこの列車に乗って、Android端末が観測したセル・RSRP・HTTP応答はどう変わるか」を後続の実測地図・グラフで確かめる。公式のエリア色を実測値として扱ったり、駅ピンを基地局として表示したりしない。

### 発表当日の予備手順

- **第一候補:** 実機計測 + BLEライブ画面。
- **BLE接続に失敗:** 事前に保存したCSVをローカルWebビューアで読み込み、実測の事後可視化を見せる。
- **実乗車データを使えない:** 明示したデモデータまたは録画を使い、架空データであることを画面と口頭で示す。
- CSVの予備データは公開リポジトリへ入れない。GPS、時刻、Cell ID等を含む生ログはローカルで管理する。

## 正確さ・公開時の注意

- Androidのセル情報は端末・SIM・モデム・OS・権限に左右される。更新が抑制されるため、すべての切り替えを取れるとは限らない。
- `cell_change`はアプリが観測した変更候補として説明する。イベントがないことだけで「ハンドオーバーがなかった」と断定しない。
- GPS速度は推定値であり、列車の公式速度ではない。トンネル・屋内・精度低下時は不明または古いデータとして表示する。
- RSRP、HTTP応答時間、GPS速度は別々の観測値。相関を示す場合も因果関係を断定しない。
- 生CSV、スクリーンショット、logcat、bugreportは公開Gitへ入れない。サンプルが必要なら座標・時刻・セル識別子を処理した合成または明示的な公開用データを作る。
- Web Bluetooth対応ブラウザとユーザー操作が必要。発表用Mac/Chromeで接続を事前確認する。
